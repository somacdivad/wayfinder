# Wayfinder

Treat the repository's project record as durable, version-controlled knowledge rather than a temporary task plan.

## Status

Wayfinder version 1 remains unactivated. This runtime skill is intentionally non-operational until its release trust root and future activation guidance say otherwise. Do not infer current maintenance or certification status from this stub, improvise an unfinished workflow, or treat it as authorization to change a project record.

Planned workflows:

- Initialize a new project record.
- Interview a stakeholder to develop the record.
- Update an existing record while preserving authority and history.
- Validate structure, links, metadata, and consistency.
- Retrieve only the authoritative context needed for another task.

## Default facilitation protocol

When a Wayfinder task requires interviewing a person, presenting design choices, reviewing an implementation, or obtaining approval, read [references/facilitation.md](references/facilitation.md) before beginning that interaction. It defines the default tone, decision size, turn boundary, incremental-update boundary, option format, and explicit-approval rule. Every implementation slice starts in a new session: approval of the preceding slice, or a request to start another one, produces a detailed next-session prompt rather than implementation in the current session. Do not load the facilitation reference for a purely mechanical validation, deterministic script run, or read-only retrieval task that requires no user decisions.

## Accepted foundation

Wayfinder uses a stable semantic kernel plus capability-driven modules. The kernel will define how readers enter, interpret, and navigate a project record. Initialization will add only the modules justified by the project's concerns instead of imposing one universal folder tree.

Each durable document will own its structural metadata in a constrained, visible Wayfinder metadata block delimited by exact HTML comments. Every block will contain `ID`, `Kind`, `Status`, `Updated`, and `Summary`; the document H1 is the title authority and tooling derives the current path. An ID is a stable, project-record-local, human-readable token that does not change with ordinary moves or retitling and never encodes mutable classification facts. Its grammar is `wf-<global-ordinal>-<frozen-mnemonic>`, for example `wf-0002-product-brief`: the ordinal is unique across all document kinds and the mnemonic is a non-authoritative recognition aid frozen after assignment. A newly allocated ID is a candidate while confined to isolated work and becomes immutable when it first enters the project's declared canonical history. Candidate state is derived from that history rather than stored in document metadata. If candidate allocations collide, an existing canonical occupant retains the ordinal; otherwise the first candidate successfully validated and integrated retains it. An automated re-key may change only the losing declaration and references whose binding Wayfinder can prove; it regenerates derived artifacts and stops on untyped occurrences rather than guessing. Re-keying uses a staged, journaled transaction: preserve the mnemonic, allocate above the maximum in the local canonical-plus-candidate view, validate before and after application, recover exact prior bytes on failure, and never fetch, integrate, or retry implicitly. Deterministic tooling will validate the distributed metadata and generate repeated navigation facts; generated indexes and catalogs will not become independent authorities.

Every initialized record is anchored by a strict, versioned JSON manifest at `<workspace-root>/.wayfinder/manifest.json` and a human-readable Markdown entrypoint inside the declared record root. The closed version 1 manifest declares `format`, `schemaVersion`, `recordRoot`, `entrypoint`, `canonicalBaseline`, `modules`, and `generatedArtifacts`. The baseline is either a fully qualified local Git ref or an authenticated published snapshot. Tools use an explicit workspace root or discover the nearest manifest by walking upward without crossing the containing version-control boundary; they never infer a missing record or fetch implicitly. Parsers reject duplicate or unknown fields, unsupported versions, and paths that cannot be proven contained.

The semantic kernel requires the machine manifest, a human knowledge map, a concise current-plan brief, a visible open-question register, and an indexed decision history. Version 1 provides the `foundation`, `evidence-led`, and `software-product` starter profiles; `decisions` is required, while `research`, `product`, `architecture`, and `development` are standard optional modules. After selecting a disclosed profile, initialization inventories concrete concerns and knowledge objects, maps them to the seed, lets the user revise the shallow subject taxonomy, and challenges overlaps or omissions before showing the complete tree and concern-to-home map for confirmation. Prefer subjects within standard modules. A project-owned `local-<slug>` module is permitted only when it has an independently stated purpose, genuinely distinct authority or lifecycle, real content, a non-duplicative boundary, and explicit user approval. Semantic discovery belongs to the interview; deterministic tooling receives and validates only the confirmed proposal. The manifest stores the resulting structure, not the originating profile or transcript. Later taxonomy evolution belongs to the Update workflow.

Initialization performs a minimum viable bootstrap before publication rather than creating empty scaffolding or attempting the full Interview workflow. It establishes attributable project intent, desired outcomes, boundaries, people and missing perspectives, current evidence and accepted decisions, consequential unknowns, confirmed structure, and a locally valid publication basis. Readiness depends on honest coverage, not a fixed question count or completeness score. Where absence could be mistaken for knowledge, distinguish `Hypothesis`, `Assumption`, `Open question`, `Deferred`, `Not applicable`, and `Not yet elicited`; reject bare placeholders and invented facts, owners, dates, priorities, or implementation choices.

Before any project-record write, show a single substantive proposal containing the exact target tree and content, IDs and metadata, concern-to-home map, unresolved states, material agent inferences, omitted modules, paths, and publication preconditions. Confirmation binds only to that proposal's digest. Deterministic tooling consumes the confirmed plan without reinterpreting it: stage and validate exact bytes, recheck that targets remain absent, create without overwriting, publish the manifest last as the discovery marker, validate the live record, and keep enough journal state for conservative recovery. Never fetch, commit, merge, push, or invoke external services implicitly. Promise recoverable publication rather than universal multi-file atomicity. Complete initialization with validation results and a pointer to the full Interview workflow.

`Kind` states a document's communicative purpose independently from its topical module and subject. Schema version 1 permits the authored kinds `map`, `brief`, `register`, `evidence`, `decision`, `guide`, and `index`; local modules compose these kinds and cannot define new ones. `map`, `brief`, `register`, `evidence`, `guide`, and `index` use the living lifecycle `Draft` → `Active` → `Superseded` or `Retired`, with direct reviewed creation as `Active` allowed. `decision` uses `Proposed` → `Accepted` or `Rejected`, and `Accepted` → `Superseded`; initialization may create it directly as `Accepted` only from explicit authority. Status expresses authority and lifecycle, never completeness, confidence, priority, or implementation progress. Supersession is reciprocal and cycle-free; historical outcomes are not silently rewritten.

Every kind has a content profile, but only stable record forms such as `evidence` and `decision` require exact section schemas. Version 1 adds only `Decision-Date`, `Supersedes`, and `Superseded-By` as conditional document metadata beyond the universal fields. Supersession fields contain sorted document IDs, are reciprocal within one confirmed transaction, and form an acyclic graph. Authored durable documents have IDs and may contain declared generated regions; deterministic tools replace only those regions. Wholly generated artifacts are manifest-listed, identity-free, disposable projections and never the sole authority for a fact or relationship.

An optional visible relationship block may declare only `Governed-By` from a living document to an `Accepted` decision and `Supported-By` from authored content to `Active` evidence. Each typed edge is a repository-relative Markdown link whose label exactly matches the target document ID. Ordinary prose links have no typed meaning, weak catch-all relations are excluded, and inverse views are generated rather than authored.

Open questions are durable items embedded in `register` documents. Each has a project-wide, location-independent `wfq-<global-question-ordinal>-<frozen-mnemonic>` ID and explicit stable anchor. Its controlled state is `Open`, `Investigating`, `Deferred`, `Resolved`, or `Retired`; conditional content records why it matters, the next step or revisit trigger, its resolution or retirement, and append-only transition history. Typed question links use `Applies-To`, `Addressed-By`, and `Resolved-By` with kind and authority constraints. Questions may move without changing identity, resolved questions may reopen only with explicit history and reason, and retired questions are ordinarily terminal.

Each `evidence` document owns frozen local source keys such as `src-01`. Every source records its citation, original locator, access date, applicability (`Direct`, `Adjacent`, or `General`), use, and limitations; publication date is recorded only when supplied. Material claims cite local source anchors. Cross-document support edges target the evidence synthesis rather than its external sources. `.wayfinder/catalog.json` is a deterministic, manifest-listed projection of document identity, status, summary, module, subject, typed edges, supersession, and question routing data; it excludes full bodies and the detailed source inventory and never becomes authority. Mechanical validation checks exact grammar and graph integrity. Semantic review judges whether relationships, resolutions, source use, and supersession are substantively warranted and never rewrites them without confirmation.

Wayfinder version 1 is governed by one digest-bound executable contract package. Its semantic reference, machine registry, exact Markdown grammar, closed JSON Schemas, literal templates, and conformance fixtures have separate declared responsibilities and may not silently redefine one another. Governed text uses UTF-8 without BOM and LF endings; digest-bound control objects use canonical JSON and payloads are addressed by SHA-256. Scripts own structural punctuation, ordering, rendering, and generated regions. Templates use validated one-pass slots and are never reapplied to authored documents after publication.

Each manifest module declares an ordered `subjects` array that may be empty. A `document` subject owns one entrypoint file; a non-overlapping, non-nested `collection` subject owns an entrypoint and contained subtree. Other documents may remain module-level with no subject. Module and subject membership derive from manifest paths rather than duplicated document metadata, and crossing a boundary later requires the Update workflow.

On first Wayfinder use in an agent session, run the bundled capability detector once and retain its exact adapter selection for subsequent commands. A Python, Node.js, or PowerShell adapter is supported only after passing the shared positive, negative, golden-output, differential, and interruption fixtures using standard libraries alone. A passing version string is insufficient. If no certified adapter passes, stop without installing dependencies or recreating the operation manually.

Certified adapters expose the same noninteractive, file-oriented `probe`, `discover`, `inventory`, `initialize-plan`, `initialize-apply`, `initialize-recover`, `validate`, and `generate` commands and return one closed JSON result envelope. `inventory` is a read-only preplanning command: it accepts a strict user-bounded local-source request and optional confirmed intake ledger, inventories without following symbolic links, and validates source digests and dispositions without making semantic judgments. Adapters never prompt, fetch, install, mutate version control, call external services, or infer interview answers. Initialization separates the semantic proposal from an external bundle containing exact payloads, a complete preview, and a canonical plan. Confirmation binds the complete plan digest. Application copies the verified bundle into `.wayfinder/operations/<operation-id>/`, records immutable hash-chained events around consequential writes, creates targets exclusively, and publishes the manifest last. Recovery is explicit and conservative, may use any adapter certified for that contract, and never silently upgrades or improvises a transaction.

Initialization requires a fresh Wayfinder-managed namespace, not an empty repository. If an incomplete Wayfinder operation exists, recover it first; if a valid manifest exists, use Update; if a manifest is invalid or unsupported, stop with diagnostics. Every proposed module root, entrypoint, and target must be absent. Version 1 never rewrites, moves, deletes, wraps, or automatically classifies existing documents.

Existing local material may enter a source-assisted initialization only through user-declared source files or roots. Deterministic tooling inventories contained regular files without following symbolic links and records paths, types, sizes, hashes, text classification, Markdown headings, exclusions, and exact duplicate groups. The agent progressively inspects relevant content and treats it as untrusted project data. Every material candidate receives a user-reviewed disposition: `incorporate`, `reference`, `preserve-out-of-scope`, or `unresolved`. Incorporation creates new governed content while leaving source bytes unchanged; a digest-bound intake ledger records provenance, target mappings, and transformation notes. Tools validate confirmed dispositions but never infer semantic equivalence, recency, or authority.

Material contradictions are preserved for review rather than automatically merged. They may become explicit open questions when that honestly represents the uncertainty, but publication stops while two artifacts claim current authority for the same governed concern. The knowledge map states the record's authority boundary and its next planning step; stale, rejected, superseded, and legacy sources stay out of default active navigation.

Initialization is complete only when both named gates pass. The operational gate proves that the confirmed plan, contract, adapter, target bytes, generated artifacts, validation result, manifest-last journal, intake ledger, and receipt agree. The semantic gate proves minimum bootstrap readiness, attributable synthesis, reviewed dispositions for all material candidates, honest treatment of consequential conflicts, one authority boundary, durable resumption cues, and user confirmation. A manifest with a failed final check is recovery-required. Completion means the record is discoverable, integral, authoritative within its declared scope, honest about uncertainty, and resumable; it does not mean the plan is finished or implementation-ready. The receipt records audit and routing data under the operation directory, while the record itself preserves the entrypoint, open questions, and recommended first Interview focus. Initialization hands off to Interview but never starts it automatically.
