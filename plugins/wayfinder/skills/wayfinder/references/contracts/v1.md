# Wayfinder executable contract version 1 — proposed frozen target

- **Status:** Unactivated candidate
- **Last updated:** 2026-09-13
- **Implemented surface:** Stage 0 through Slice 5

This document is the normative semantic contract for the implemented Initialize
candidate. It does not activate Initialize. JSON Schemas document closed interchange shapes;
`grammar.abnf` documents lexical tokens; `contract.json` owns registries and
governed-resource digests; fixtures provide reviewed examples; adapters are
implementations under test; certification reports are evidence rather than
authority.

## Package and text rules

- **WF-PKG-001 — Release identity.** The distribution trust root is the exact
  file `assets/contract-v1/release.json`. It must be a closed
  `wayfinder-contract-release` version 1 object with contract version 1, the
  fixed contract-manifest path, an ordered nonempty adapter registry, and an
  ordered certification array. Every adapter entry has a stable version-1 ID,
  a portable path beneath `scripts/adapters/`, and a source digest. The current
  release contains only `python-reference-v1`; Node.js and PowerShell entries
  remain absent until their implementations exist. Trust in release bytes comes
  from the containing skill distribution; the descriptor intentionally does not
  hash itself.
- **WF-PKG-002 — Complete resource set.** The release descriptor hashes the raw
  bytes of `contract.json` and the Python adapter. The contract manifest lists
  every file beneath its declared governed scopes exactly once and hashes each
  raw byte stream with SHA-256. Missing, duplicate, altered, or unlisted files
  in those scopes invalidate the package.
- **WF-PKG-003 — Authority split.** Normative prose owns semantics; schemas own
  documented JSON shapes; `known-answer.json` owns fixed probe vectors;
  conformance cases and expected results are reviewed examples; adapters are
  replaceable implementations; certification reports are local evidence.
  A frozen contract status does not certify any adapter, environment, parity
  result, adapter family, or runtime workflow. Certification entries are valid
  only after the named evidence exists; this proposed release contains none.
- **WF-PKG-004 — Cross-artifact candidate identity.** `contract.json` owns the
  positive integer candidate revision. `release.json` identifies that revision
  as `v1-candidate-revision-<revision>`. The release schema accepts exactly the
  version-1 candidate-revision grammar, the release lifecycle statuses
  `unactivated-candidate`, `unactivated-frozen`, and `activated-frozen`, the
  adapter registry, and certification entries. For revision 8 the contract
  status is `frozen` and the release status is `unactivated-frozen`; this is a
  reviewable proposal until its maintainer-owned freeze record is accepted.
  `probe` rejects a digest-valid package when the revision, lifecycle, registry,
  or schema identities disagree. Any governed byte or semantic change after
  freeze reopens the candidate, advances its revision, restores candidate
  status, invalidates every affected evidence report, and requires every adapter
  to rerun. Adding an implementation or certification without changing governed
  semantics does not change the contract digest, but still requires new
  adapter- and environment-specific evidence. Human-facing progress belongs to
  the maintainer design record.
- **WF-TEXT-001 — Encoding.** Governed text and JSON are well-formed UTF-8 with
  no BOM. Lone surrogates and malformed byte sequences are errors.
- **WF-TEXT-002 — Newlines.** Governed package resources use LF only and exactly
  one terminal LF. Manifest inputs use LF only; a terminal LF is optional.
- **WF-TEXT-003 — Normalization.** All strings accepted from JSON inputs are NFC.
  Validation rejects rather than normalizes non-NFC input.

## JSON and command rules

- **WF-JSON-001 — Strict parsing.** JSON must use the RFC 8259 grammar. Duplicate
  object names, comments, trailing commas, non-finite values, and malformed
  strings are rejected.
- **WF-JSON-002 — Closed objects.** Every version-1 control object is closed.
  Unknown and missing required members are errors.
- **WF-JSON-003 — Version selection.** `schemaVersion` is the integer 1. Boolean
  values are not integers. Other versions fail closed.
- **WF-JSON-004 — Numeric subset.** Version 1 accepts only integers in the exact
  range -(2^53-1) through 2^53-1. Decimal points, exponents, `NaN`, and infinity
  spellings are forbidden even when the mathematical value is integral.
- **WF-JSON-005 — Canonical JSON.** Canonical bytes are UTF-8 without BOM or a
  trailing newline. Objects are ordered by UTF-16 code units; arrays retain
  order; strings use JSON escaping without escaping `/` or non-ASCII scalar
  values; integers use base-10 with no leading zero or negative zero; separators
  are `,` and `:` with no whitespace. Version-1 user-controlled collections are
  represented as ordered arrays rather than dynamic maps.
- **WF-CMD-001 — Result envelope.** Every invocation writes exactly one closed
  `wayfinder-command-result` version 1 object followed by LF to stdout. Required
  members, in display order, are `format`, `schemaVersion`, `ok`, `command`,
  `code`, `data`, and `diagnostics`. Diagnostics are an ordered array of closed
  objects with `code`, `message`, and optional `path`, `field`, `expected`,
  `actual`, and `remediation`.
- **WF-CMD-002 — Streams and determinism.** Human-readable failure summaries go
  to stderr. stdout contains no prompt, traceback, progress text, or second JSON
  value. Deterministic fields are byte-stable for identical inputs; runtime and
  physical-path evidence is explicitly nested under environment data.
- **WF-CMD-003 — Exit classes.** Exit 0 is success; 2 is command/input-contract
  error; 3 is precondition/conflict; 4 is record-validation failure; 5 is
  recovery required; and 70 is an unexpected internal failure. Stable JSON
  diagnostic codes carry the precise reason.
- **WF-CMD-004 — Read-only boundary.** `probe`, `discover`, and `inventory` never prompt, use
  the network, install software, invoke external services, mutate version
  control, or write a project record.

## Probe rules

- **WF-PROBE-001 — Identity verification.** `probe` verifies the fixed release
  descriptor, its expected version and status, the exact contract manifest and
  adapter paths and digests, and every governed resource before reporting
  success.
- **WF-PROBE-002 — Known answers.** `probe` recomputes every registered version-1
  SHA-256, canonical-JSON, NFC, and safe-path vector. A version string alone is
  never sufficient.
- **WF-PROBE-003 — Capabilities.** The result separates deterministic contract
  identity and known-answer results from environment evidence. Required Python
  capabilities are UTF-8 strict decoding, SHA-256, NFC normalization, filesystem
  physical resolution, and symbolic-link inspection.

## Discovery rules

- **WF-DISC-001 — Exact root.** `--workspace-root` names one exact directory
  after physical resolution. It must contain `.wayfinder/manifest.json`; it is
  not a search hint.
- **WF-DISC-002 — Physical start.** Without an explicit root, discovery starts
  at `--start` or the current directory. A supplied regular-file start uses its
  parent. The start is resolved physically before traversal.
- **WF-DISC-003 — Upward search.** Discovery checks each directory, including the
  stop directory, and selects the nearest `.wayfinder/manifest.json`. Without a
  Git worktree boundary it stops at the filesystem root.
- **WF-DISC-004 — Git boundary.** The containing Git worktree is the nearest
  ancestor with a `.git` directory or regular-file marker. Discovery checks that
  ancestor and never examines its parent. A symbolic-link `.git` marker is a
  conservative boundary but is never followed.
- **WF-DISC-005 — Invalid nearest record.** Once the nearest manifest path exists,
  its validation result is final. An invalid candidate never permits fallback to
  a parent record.
- **WF-DISC-006 — Discovery symlinks.** A symbolic-link `.wayfinder` component or
  manifest is rejected. Declared managed paths reject every existing symbolic
  link component rather than following it.
- **WF-DISC-007 — No inference and no writes.** Discovery never infers a workspace
  from `docs`, README files, or familiar names and performs no write.

## Manifest rules

- **WF-MAN-001 — Root shape.** The manifest is a closed object whose exact fields
  are `format`, `schemaVersion`, `recordRoot`, `entrypoint`,
  `canonicalBaseline`, `modules`, and `generatedArtifacts`. Format is
  `wayfinder-project-record`; schema version is 1.
- **WF-MAN-002 — Baselines.** A `git-ref` baseline contains only `kind` and a
  fully qualified `refs/...` value. A `snapshot` contains only `kind`, a
  workspace-relative path beneath `.wayfinder/baselines/`, and a lowercase
  64-hex SHA-256 value. A discovered live record requires the declared snapshot
  file to exist; the later pre-publication initializer exception is outside this
  slice.
- **WF-MAN-003 — Identifiers.** Module IDs are the registered standard IDs or
  `local-<lowercase-ascii-slug>`. Module IDs are unique. Subject IDs are
  lowercase ASCII slugs and unique within their module. Arrays preserve declared
  navigation order.
- **WF-PATH-001 — Portable relative paths.** Managed paths use `/`, are NFC, and
  contain only portable ASCII segments made from letters, digits, `.`, `_`, and
  `-`. They reject absolute and drive/UNC paths, backslashes, NUL, empty, `.` or
  `..` segments, trailing dot or space, Windows device names, and `:`. The sole
  exception is complete `recordRoot: "."`. Path identity and overlap checks use
  ASCII case-insensitive comparison to prevent case-only aliases.
- **WF-PATH-002 — Containment.** `recordRoot` is workspace-relative. All other
  manifest paths except snapshot paths are record-relative. Snapshot paths are
  workspace-relative. Lexical containment is proven first. Every existing path
  component is then inspected without following symbolic links, and physical
  resolution must remain beneath its declared owner.
- **WF-MAN-004 — Modules.** `modules` contains the required `decisions` module
  and may contain registered `research`, `product`, `architecture`,
  `development`, or approved-shape local modules. Module roots are pairwise
  non-overlapping and non-nested. Each module entrypoint is contained in its
  root. Module fields are `id`, `root`, `entrypoint`, and `subjects`.
- **WF-MAN-005 — Subjects.** `subjects` is required and may be empty. A
  `document` subject contains only `id`, `kind`, and `entrypoint`. A `collection`
  subject additionally contains `root`. Collection roots are contained in the
  module root and are pairwise non-overlapping and non-nested. Document subject
  entrypoints may not fall within a collection root. Every subject entrypoint is
  contained in its owner.
- **WF-MAN-006 — Entrypoints.** The record, module, and subject entrypoints end in
  `.md`. Case-insensitive duplicate entrypoints are rejected. In a discovered
  live record, every declared entrypoint must exist as a regular file and every
  declared root must exist as a directory.
- **WF-MAN-007 — Generated artifacts.** Each closed artifact object contains
  `path` and `generator`. Paths are unique and record-contained. Version 1
  registers only `document-catalog-v1`. A live artifact must exist as a regular
  file, may not be symbolic, and may not collide with an authored entrypoint.

## Source inventory rules

- **WF-INV-001 — Command interface.** `inventory` requires exactly one existing
  physical directory through `--workspace-root` and one non-symbolic regular
  request file through `--request`; `--ledger` optionally names one
  non-symbolic regular intake-ledger file. The command is read-only and returns
  the canonical inventory, its SHA-256, and physical workspace identity. When a
  ledger is supplied it also returns the normalized ledger, ledger SHA-256,
  disposition counts, and number of source digests rechecked.
- **WF-INV-002 — Bounded selections.** An inventory request is a closed
  `wayfinder-source-inventory-request` version 1 object containing nonempty,
  unique workspace-relative NFC source `selections`, unique `targetRoots`, and
  explicit positive `maxEntries`, `maxFileBytes`, `maxTotalBytes`, and
  `maxDepth` limits. Paths use `/`, reject absolute, drive/UNC, empty, `.`,
  `..`, backslash, and NUL forms, and are resolved only beneath the exact
  physical workspace. The tool never defaults to the whole workspace.
- **WF-INV-003 — Classification and traversal.** Each selected entry is
  classified with `lstat` as `regular-file`, `directory`, `symlink`, or
  `unsupported-file`. Directories are traversed recursively in UTF-8 byte order.
  Selections and overlapping roots are de-duplicated by exact normalized
  workspace-relative path. Symbolic links are recorded but
  never opened or followed at the selection, directory, or file level.
- **WF-INV-004 — Exclusions.** `.git`, `.hg`, and `.svn` administration;
  `.wayfinder` state; declared target roots; secret names matching `.env`,
  `.env.*`, private-key/credential patterns; dependency directories
  `node_modules`, `vendor`, `.venv`, and `venv`; build-output directories
  `build`, `dist`, `out`, `target`, `coverage`, and `.cache`; registered archive
  suffixes; symbolic links; and unsupported special files are listed with a
  stable exclusion reason. An explicitly selected ordinary regular file may
  override only dependency, build-output, or archive exclusions. It can never
  override containment, VCS, `.wayfinder`, target-root, secret, symlink, or
  special-file safety exclusions.
- **WF-INV-005 — Regular-file identity.** Every included regular file records
  byte length and lowercase SHA-256. It is opened without symbolic-link
  following where the runtime provides that primitive, and type, identity,
  size, and modification observations are rechecked around the read. A race or
  unreadable file fails as a precondition conflict rather than returning a
  partial inventory. Excluded regular files may expose byte length from
  metadata but are never opened and have no digest or content classification.
- **WF-INV-006 — Text and Markdown cues.** Included bytes that decode with the
  strict UTF-8 decoder are `strict-utf8`; all others are `opaque-bytes`.
  Included `.md` text receives Markdown cues only when the decoded text is NFC.
  Version 1 extracts nonempty CommonMark-style ATX headings of levels 1–6
  outside backtick or tilde fenced code blocks, records level, text, and
  one-based line, removes a valid closing hash sequence, and chooses the first
  level-1 heading as `h1`. It performs no prose interpretation.
- **WF-INV-007 — Duplicates and ordering.** Exact duplicate groups contain every
  included regular-file path sharing a SHA-256 and contain at least two paths.
  Entries and selections sort by UTF-8 bytes of normalized paths; duplicate
  groups sort by digest and then paths. Files reached through duplicate or
  overlapping selections appear once. No semantic or near-duplicate grouping
  is performed.
- **WF-INV-008 — Limits and failure atomicity.** Exceeding entry, per-file,
  cumulative included-byte, or traversal-depth limits returns exit class 3 with
  a stable `inventory.limit-*` diagnostic and no partial success. Invalid
  request or ledger structure returns exit class 2. Unexpected failures return
  exit 70 without traceback text. Every outcome preserves source bytes,
  project-record bytes, package bytes, Git state, and external systems.

## Intake-ledger rules

- **WF-INTAKE-001 — Closed ledger.** An intake ledger is a closed
  `wayfinder-intake-ledger` version 1 object containing the exact canonical
  inventory SHA-256 and a source array. Source paths are unique and must name
  included regular files in that inventory. Each closed source record contains
  `path`, `sha256`, `byteLength`, `disposition`, nonempty review `reason`,
  `targetIds`, nullable `transformationNote`, `evidenceKeys`, and `questionIds`.
- **WF-INTAKE-002 — Confirmed dispositions.** The only dispositions are
  `incorporate`, `reference`, `preserve-out-of-scope`, and `unresolved`.
  `incorporate` requires at least one valid `wf-` target ID and a nonempty
  transformation note. `reference` requires at least one `src-` evidence key
  and forbids target IDs and transformation notes. `preserve-out-of-scope`
  forbids mappings, evidence keys, question IDs, and transformation notes.
  `unresolved` requires at least one valid `wfq-` question ID and forbids target
  IDs, evidence keys, and transformation notes. Arrays reject duplicates.
- **WF-INTAKE-003 — Digest recheck.** Ledger validation first proves the ledger
  byte length and SHA-256 agree with the bound inventory, then safely reopens
  every ledger source and recomputes both values. Missing, replaced, symbolic,
  or changed sources return exit class 3 with `intake.source-stale`.
- **WF-INTAKE-004 — Semantic authority boundary.** The adapter validates only
  confirmed syntax, bindings, and bytes. It never infers materiality, semantic
  equivalence, authority, disposition, taxonomy placement, transformation
  meaning, evidence relevance, question meaning, or conflict resolution.

## Record and identifier rules

- **WF-ID-001 — Document IDs.** A document ID is
  `wf-<ordinal>-<mnemonic>`. The ordinal is decimal, at least four digits, and
  at least 1; values below 1000 use exactly four digits. The mnemonic is a
  1–48 character lowercase ASCII slug. Complete IDs and ordinals are unique.
- **WF-ID-002 — Question IDs.** Question IDs use the same rules with `wfq-`
  and a project-wide sequence independent from document IDs. Source keys use
  `src-` plus at least two digits, are at least 1, and are unique within one
  evidence document.
- **WF-ID-003 — Candidate allocation.** `generate` action `allocate` scans the
  validated local record and returns consecutive `max + 1` document and
  question candidates in request order without writing. ASCII words from the
  title produce a mnemonic at word boundaries; an explicit mnemonic is
  required when no safe result exists. Returned IDs are candidates; this slice
  performs no integration or canonical-history mutation and never fills gaps.

## Authored Markdown rules

- **WF-DOC-001 — Exact envelope.** Every authored document is UTF-8, LF, NFC,
  has exactly one terminal LF and no trailing whitespace, starts with exactly
  one H1, one blank line, then exactly one metadata block. The exact delimiters
  are `<!-- wayfinder:metadata -->` and `<!-- /wayfinder:metadata -->`.
- **WF-DOC-002 — Metadata fields.** Fields use exact
  `- **Name:** value` lines in this order: `ID`, `Kind`, `Status`, `Updated`,
  `Summary`, then applicable `Decision-Date`, `Supersedes`, and
  `Superseded-By`. Universal fields are required; duplicates, unknown fields,
  empty values, malformed lines, and order deviations fail.
- **WF-DOC-003 — Kinds and lifecycle.** Authored kinds are `map`, `brief`,
  `register`, `evidence`, `decision`, `guide`, and `index`. All but `decision`
  admit `Draft`, `Active`, `Superseded`, and `Retired`. Decisions admit
  `Proposed`, `Accepted`, `Rejected`, and `Superseded`. Accepted, Rejected, and
  Superseded decisions require `Decision-Date`; Proposed decisions forbid it.
  Other kinds always forbid it. `Superseded` requires `Superseded-By`.
- **WF-DOC-004 — Stable content profiles.** Evidence documents contain, once
  and in order, `Question and scope`, `Method`, `Findings`, `Applicability and
  limitations`, `Evidence, inference, and hypothesis`, `Implications`,
  `Unknowns`, `Next validation`, and `Sources` H2 sections. Decision documents
  contain `Context`, `Options considered`, `Decision`, `Rationale`,
  `Consequences`, `References`, and `Supersession`. Flexible kinds retain
  user-selected H2 content.

## Relationships, questions, and sources

- **WF-REL-001 — Relationship block.** At most one optional relationship block
  immediately follows metadata and one blank line. It uses exact delimiters,
  exact field lines, and only `Governed-By` then `Supported-By`, ordered by
  relation then numeric target ID. Each line contains one normalized relative
  Markdown link whose label equals the target ID. Duplicate edges fail.
- **WF-REL-002 — Relationship targets.** `Governed-By` targets an `Accepted`
  decision. `Supported-By` targets `Active` evidence. The ID and resolved path
  must name the same contained authored document.
- **WF-SUP-001 — Supersession.** Supersession metadata is a numeric-ID-sorted,
  duplicate-free exact comma-space list. Targets exist in the same lifecycle
  family, self-edges fail, every edge is reciprocal, and the graph is acyclic.
- **WF-Q-001 — Question blocks.** Question blocks occur only in `register`
  documents. Each exact block contains an equal ID anchor and ID field, one H3
  title, ordered fields, project-unique ID/ordinal, and either one or more
  `Applies-To` links or `Scope: Record-Wide`.
- **WF-Q-002 — Question lifecycle.** States are `Open`, `Investigating`,
  `Deferred`, `Resolved`, and `Retired`. State-specific exact H4 sections are
  enforced. `Resolved` alone requires `Resolution-Date` and `Resolved-By`.
  `Retired` is terminal. History lines use
  `- YYYY-MM-DD: From -> To - reason`, begin with `None` on the Raised date,
  form a continuous allowed transition chain, and end at the current state.
  Reopening `Resolved -> Open` requires a reason containing `reopen`.
- **WF-Q-003 — Question targets.** Typed question links use exact ID/path
  bindings. `Addressed-By` targets evidence. `Resolved-By` targets an Accepted
  decision or Active evidence/brief. Duplicate edges fail.
- **WF-SRC-001 — Evidence sources.** Exact source blocks occur only in evidence
  documents. Each has an equal `src-NN` anchor and H3 key, ordered required
  `Citation`, `Original`, `Accessed`, and `Applicability` fields, optional
  `Published`, and nonempty `Used for` and `Limitations` H4 sections.
  Applicability is `Direct`, `Adjacent`, or `General`; Original is HTTPS or a
  normalized portable workspace-relative path naming a present non-symbolic
  regular file contained beneath the workspace root.
- **WF-SRC-002 — Citation integrity.** Local citations use exact
  `[src-NN](#src-NN)` syntax and must resolve uniquely. Every explicitly marked
  `- **Material claim:**` line contains at least one such citation. Unused
  source entries produce stable warnings; determining which unmarked prose is
  material or whether a source supports it remains semantic review.

## Containment, templates, and generation

- **WF-REC-001 — Authored containment.** The record entrypoint is a `map`.
  Other authored Markdown files directly beneath the record root are kernel
  documents with null module and subject membership, as required by the
  `foundation` and `evidence-led` profiles. Every nested authored document
  belongs to exactly one manifest module by path. A document subject owns its
  entrypoint; a collection subject owns contained documents; other module
  documents have null subject membership. Membership is derived from paths.
- **WF-TPL-001 — Literal templates.** Each authored kind has one governed
  literal template with exactly one each of `TITLE`, `METADATA_BLOCK`,
  `RELATIONSHIP_BLOCK`, and `CONTENT`. Rendering validates a closed structured
  request, substitutes once, rejects missing, duplicate, unknown, recursive, or
  unexpanded reserved slots, and does not normalize or rewrite supplied prose.
- **WF-TPL-002 — Render writes.** `generate` action `render` requires an explicit
  existing output root and explicit portable output paths. It validates every
  rendered document before writing, rejects duplicate or existing outputs, and
  writes nowhere else. Structured typed-link destinations are normalized
  relative to the owning output document, matching the authored parser; `..`
  is permitted only when the normalized destination remains inside the record.
- **WF-GEN-001 — Generated regions.** Only `map` and `index` may contain
  nonnested uniquely named regions using the exact `document-index-v1`
  delimiter and input digest. The entire start-to-end region is replaceable;
  every byte outside it is preserved. Region membership derives from the owner:
  module entrypoints for a root map, module documents for a module index, and
  subject members for a subject index.
- **WF-GEN-002 — Catalog.** `document-catalog-v1` emits pretty UTF-8/LF JSON
  with a generated marker, canonical input digest, documents ordered by numeric
  ID, complete routing fields, and questions ordered by numeric question ID.
  It excludes document bodies and detailed source inventories.
- **WF-GEN-003 — Stable projections.** Validation recomputes catalogs and
  regions and rejects drift. `generate` action `catalog` writes only exact
  manifest-declared catalog artifacts. Action `regions` writes only explicit
  authored paths already containing recognized regions. Repeated generation is
  byte-idempotent.

## Slice 3 command and safety rules

- **WF-CMD-005 — Validate interface.** `validate --workspace-root PATH` reads
  one exact live record, performs the Slice 3 structural and graph checks, and
  writes nothing. Validation failures use exit 4.
- **WF-CMD-006 — Generate interface.** `generate --workspace-root PATH
  --request FILE [--output-root PATH]` accepts one closed
  `wayfinder-generation-request`. Actions are `allocate`, `render`, `catalog`,
  and `regions`; action-specific fields are closed. Expected input errors use
  exit 2 and conflicts use exit 3.
- **WF-CMD-007 — Side-effect boundary.** Slice 3 commands never prompt, use a
  network, install dependencies, invoke external services, modify project
  records outside declared generation targets, or mutate Git. Rejected
  validation and preflight do not write. Unexpected exceptions map to exit 70
  with one result object and no traceback.
- **WF-SEM-001 — No semantic inference.** The adapter never infers kind,
  status, evidence relevance, relationship justification, question resolution,
  taxonomy membership, lifecycle transitions, or materiality. It checks only
  explicit syntax, declared paths, state histories, and graph constraints.

## Slice 4 proposal and planning rules

- **WF-INIT-001 — Initialize-plan interface.** `initialize-plan
  --workspace-root PATH --proposal FILE --bundle-root PATH` accepts one strict,
  non-symbolic proposal file and exclusively creates one previously absent
  bundle directory. It writes no target-record path. Rejected preflight writes
  nothing.
- **WF-PROP-001 — Closed confirmed proposal.** A
  `wayfinder-initialize-proposal` version 1 object is closed at every governed
  level. It names `fresh` or `source-assisted` mode, one explicitly confirmed
  registered profile, an explicit effective date, the complete manifest,
  complete structured authored-document declarations, and semantic-review
  declarations. The adapter validates confirmed choices; it never selects a
  profile, taxonomy, disposition, meaning, status, evidence relevance, or
  authority outcome.
- **WF-PROP-002 — Complete normalized structure.** Authored paths, document
  IDs, and question IDs are unique. Greenfield candidate ordinals occur in
  proposal order, begin at 1, and contain no gaps. The complete Slice 3 model is
  validated against an isolated virtual record. Every concern has exactly one
  existing document or question home. Every disabled standard module has one
  stated omission reason.
- **WF-PROP-003 — Honest readiness and resumption.** The proposal carries
  applicable epistemic states, a nonempty authority boundary, disclosed
  material agent inferences, all eight bootstrap-readiness predicates, and a
  durable Interview summary with existing focus IDs. Material inferences must
  be confirmed. An `explicit-unresolved` predicate requires a durable question.
  Competing current authority blocks planning.
- **WF-PROP-004 — Source-assisted binding.** Fresh proposals forbid inventory
  and intake bindings; source-assisted proposals require both. Each binding is
  a workspace-relative regular-file path and canonical-JSON SHA-256. Planning
  rebuilds and compares the inventory, validates the intake ledger and current
  source bytes, requires every proposal-declared material source to have one
  ledger disposition, and proves intake document, question, and evidence-key
  bindings resolve uniquely. It never infers materiality, a disposition, or a
  transformation. Canonical inventory and intake bytes are copied into a
  source-assisted bundle and bound through the plan.
- **WF-PLAN-001 — Exact payload bundle.** A successful bundle contains
  canonical `plan.json`, deterministic `preview.md`, and ordinal files beneath
  `payload/`. Every authored document, generated artifact, and the one manifest
  payload has one plan entry with final target, bundle path, role, optional
  document ID, byte length, SHA-256, and producer identity/digest. Payload and
  target paths are unique and complete.
- **WF-PLAN-002 — Virtual validation and review projection.** Planning renders
  exact authored bytes, replaces generated regions, renders generated
  artifacts, and runs the complete Slice 3 validator in isolation. The plan
  retains the profile, concern homes, epistemic states, omissions, authority
  boundary, inferences, readiness, exact target tree, validation projection,
  and Interview pointers. The preview displays these facts and full authored
  bytes.
- **WF-PLAN-003 — Preconditions and future operation order.** Planning records
  physical workspace and record-root identities, manifest absence, target and
  module-root absence, and source/intake/baseline bindings. It rejects existing
  or symbolic targets, an existing manifest, stale sources, nonempty prior
  operation state, containment failures, and an existing bundle. The future
  operation list creates directories, creates non-manifest payloads without
  overwrite, and publishes the manifest last. Slice 4 executes none of it.
- **WF-PLAN-004 — Canonical digest and non-circular preview.** `plan.json` is
  exact canonical JSON without terminal LF. Its raw SHA-256 is the confirmation
  digest and binds the contract, proposal, preconditions, review, operation
  order, and every target payload digest. The ordinary operation ID is
  `wfinit-` plus the first 24 digest hex digits. `preview.md` displays both but
  is a deterministic review projection, not a target payload or digest input.
  This avoids the circular requirement that a digest-bearing preview hash
  itself before its digest exists.
- **WF-PLAN-005 — Explicit deterministic controls.** Effective date is proposal
  data, never a hidden clock read. Maintainer-only operation-ID injection is
  accepted only under `WAYFINDER_TEST_MODE=1`, uses `wfinit-test-<slug>`, and is
  exposed in the result and preview.
- **WF-CMD-008 — Slice 4 safety boundary.** `initialize-plan` never prompts,
  fetches, installs, invokes external services, mutates sources or Git, writes
  the project record, publishes a manifest, applies a plan, creates a journal,
  or performs recovery. Unexpected exceptions map to exit 70 with one result
  object and no traceback.

## Slice boundary

The proposed frozen version-1 target provides package verification, strict JSON primitives,
results, `probe`, discovery, manifest validation, source inventory, intake
ledger validation, record parsing and validation, candidate allocation,
literal rendering, deterministic catalog/index generation, proposal
normalization, `initialize-plan`, confirmed exact-byte application, interruption
recovery, conservative rollback, and completion receipts in the Python reference
adapter. Node.js, PowerShell, runtime detection, cross-adapter comparison,
environment certification, full-family certification, and Initialize activation
remain unavailable. The frozen status identifies a parity target; it does not
make the Python adapter an oracle or a certified runtime.

## Slice 5 application and recovery rules

- **WF-APPLY-001 — Explicit confirmed interface.** `initialize-apply
  --workspace-root PATH --bundle-root PATH --plan-sha256 HEX
  --confirmation-token wayfinder-confirm-sha256:HEX` is public and
  noninteractive. Both digest occurrences must equal the raw SHA-256 of the
  exact canonical `plan.json`. The command rejects missing, duplicated, or
  additional options and never derives consent from bundle presence, preview
  prose, standard input, or an earlier invocation.
- **WF-APPLY-002 — Exact bundle import.** Apply accepts only the closed Slice 4
  bundle membership derived from the plan: `plan.json`, `preview.md`, every
  declared payload, and the two declared source attachments in source-assisted
  mode. It rejects symbolic, missing, extra, altered, noncanonical, wrong-
  contract, and wrong-workspace inputs. Every payload length and digest is
  verified before managed writes. It copies those exact bytes beneath
  `.wayfinder/operations/<operation-id>/bundle/`; it never renders, rewrites,
  normalizes, or semantically interprets proposed content.
- **WF-APPLY-003 — Complete precondition recheck.** Before acquiring the lock
  and again before live publication, Apply verifies the physical workspace and
  record-root identities, executing contract digest, locally resolved canonical
  baseline, source inventory and intake bytes, current source digests, manifest
  absence, every target and module-root absence, portable namespace containment,
  and absence of prior operation state. A changed predicate returns a stable
  conflict or recovery-required result; pre-lock rejection creates no managed
  state.
- **WF-LOCK-001 — Narrow owned lock.** The only operation lock is
  `.wayfinder/initialize.lock`, created exclusively and containing the operation,
  plan, host, process, and unguessable owner token. It is advisory for one local
  workspace, not a distributed lock. Apply never steals it. Recovery may reclaim
  it only for the same operation and plan when the recorded same-host process no
  longer exists; malformed, foreign, live, mismatched, or ownership-changed
  locks block automated mutation.
- **WF-JOURNAL-001 — Immutable hash-chained events.** Each operation owns one
  append-only UTF-8/LF `events.jsonl`. Every canonical event contains its
  operation ID, one-based sequence, UTC whole-second timestamp, type, preceding
  event digest, closed data, and an SHA-256 over the event excluding that final
  digest. The first event records the confirmed plan, target set, exact intended
  targets and digests, and whether the control root was created. Sequence,
  predecessor, digest, canonical encoding, recognized type, target order, and
  state transitions are validated before recovery trusts the journal.
- **WF-STAGE-001 — Private exact-byte staging.** The operation and staging
  directories are created with owner-only permissions where supported and the
  staging directory is verified to share the workspace filesystem. Every exact
  payload is staged and byte-verified; the complete staged record reproduces
  the plan's validation projection before publication. Staging and validation
  never mutate source or target bytes.
- **WF-PUBLISH-001 — Exclusive manifest-last publication.** Apply follows the
  exact declarative operation list. It creates absent directories, then each
  non-manifest file with exclusive no-clobber creation, flushes and byte-verifies
  it, and publishes `.wayfinder/manifest.json` exclusively only after all other
  targets match. Pre/post events surround every file and manifest publication.
  Before the manifest event and bytes, discovery must expose no record.
- **WF-COMPLETE-001 — Two completion gates.** After manifest publication,
  Apply regenerates the deterministic projections in memory, validates the live
  record, and rechecks every target byte. Operational integrity passes only when
  plan, contract, adapter, baseline, source bindings, target set, generated
  artifacts, manifest-last journal, validation, intake, and receipt agree.
  Semantic readiness passes only from the confirmed plan's eight readiness
  predicates, authority confirmation, reviewed dispositions, conflict boundary,
  and durable Interview pointers. A published manifest with either gate
  incomplete is recovery-required, never silently complete.
- **WF-RECEIPT-001 — Deterministic durable receipt.** After both gates pass,
  Apply exclusively writes canonical
  `.wayfinder/operations/<operation-id>/receipt.json`, records its digest, and
  appends terminal `complete`. The receipt binds operation, plan, contract,
  adapter, baseline, manifest, target-set, intake counts, validation result,
  both gates, entrypoint, open questions, and the next `interview` workflow with
  recommended focus IDs. With injected time fixed, equivalent operations yield
  byte-identical receipts. The receipt is audit and routing data, not semantic
  project authority.
- **WF-RECOVER-001 — Explicit classification and action.**
  `initialize-recover --workspace-root PATH --operation-id ID --action
  inspect|resume|rollback` never chooses a mutating action implicitly. `inspect`
  is repeatable and read-only and returns exactly one of `resumable`,
  `completed`, `rolled-back`, `blocked`, or `manual-recovery`. Resume is allowed
  only when the imported bundle and journal validate, all event-owned live paths
  retain exact planned bytes, every not-yet-created target remains absent, and
  current baseline/source predicates still pass.
- **WF-RECOVER-002 — Conservative rollback.** Rollback removes a published
  manifest first and only when its exact bytes and creation event match. It then
  removes, in reverse order, only exact unchanged files with completed creation
  events and empty directories with completed creation events. Pre-existing,
  unowned, unexpectedly missing, nonempty, symbolic, or externally modified
  paths are preserved and reported as manual recovery. Operation audit state is
  retained. Repeated inspection and interrupted rollback never widen removal.
- **WF-RECOVER-003 — Reachable interruption outcomes.** Maintainer-only failure
  injection is gated by `WAYFINDER_TEST_MODE=1` and exists after lock acquisition,
  bundle recording, staging boundaries, the second preflight, publication start,
  every directory and file pre/post boundary, manifest pre/post publication,
  live-validation pre/post, receipt, completion, and rollback removals. Every
  injected state has a fixture-proven `resumable`, `blocked`, `manual-recovery`,
  `completed`, or `rolled-back` outcome. A missing post-event, corrupted or
  forked chain, or unexplained live path is never inferred successful.
- **WF-CMD-009 — Slice 5 result and side-effect boundary.** Apply and recovery
  emit exactly one closed JSON result object on stdout. Expected input errors use
  exit 2, changed preconditions use exit 3, structural live-record errors use
  exit 4, recovery/interruption/manual-action states use exit 5, and unexpected
  exceptions use exit 70 without traceback output. They never prompt, fetch,
  install dependencies, call external services, mutate sources or unrelated
  bytes, or invoke Git. The guarantee is recoverability and no overwrite, not
  universal multi-file atomicity.
